## Постановка задачи и модель

Работа выполнена по теме № 8 — **«Ситуации полной неопределённости и базовое моделирование»** ([методические материалы](./sources/Список%20направлений%20исследования.pdf)). Исследуется разработка мобильного приложения (MVP) с нуля при отсутствии исторической статистики по прошлым проектам.

Процесс состоит из четырёх последовательных этапов (`design`, `dev`, `qa`, `mkt`). Для каждого этапа заданы две независимые непрерывные случайные величины — длительность `T` (дни) и стоимость `C` (тыс. ₽). Итого модель включает **8 исходных случайных величин** и две аддитивные результирующие характеристики:

```text
T_total = T_design + T_dev + T_qa + T_mkt
C_total = C_design + C_dev + C_qa + C_mkt
```

- **Выбор распределений:** при известных только границах `[a, b]` используется непрерывное равномерное распределение (`uniform`); при наличии экспертной оценки наиболее вероятного значения `c` — треугольное распределение (`triang`). Дискретное равномерное распределение рассматривается в теоретическом разделе отчёта, но не вводится в прикладную модель непрерывных сроков и затрат.
- **Проектные ограничения:** срок `MAX_DAYS = 60` дней и бюджет `MAX_BUDGET = 1200` тыс. ₽.
- **Метод исследования:** на базе `N_SIM = 10 000` прогонов Монте-Карло с фиксированным зерном `SEED = 42` оцениваются вероятности нарушения ограничений (`P_over_days`, `P_over_budget`) и вероятность одновременного соблюдения обоих условий (`P_success`).

## Параметры модели и сценарии

Все числовые параметры зафиксированы в [`config.py`](./config.py). Для анализа компромисса «срок–стоимость» сравниваются два сценария:

- **`BASE`** — базовый план разработки.
- **`ACCEL`** — what-if сценарий ускорения этапа разработки (`dev`) за счёт привлечения дополнительного ресурса.

| Этап | Метрика | Сценарий `BASE` | Изменение в `ACCEL` |
| :--- | :--- | :--- | :--- |
| **Дизайн (`design`)** | Срок `T`, дн. | `uniform(5, 12)` | Без изменений |
| | Стоимость `C`, тыс. ₽ | `triang(80, 110, 160)` | Без изменений |
| **Разработка (`dev`)** | Срок `T`, дн. | `triang(18, 25, 40)` | `triang(14, 18, 26)` |
| | Стоимость `C`, тыс. ₽ | `triang(400, 550, 850)` | `triang(500, 680, 950)` |
| **Тестирование (`qa`)** | Срок `T`, дн. | `uniform(6, 14)` | Без изменений |
| | Стоимость `C`, тыс. ₽ | `uniform(100, 180)` | Без изменений |
| **Маркетинг (`mkt`)** | Срок `T`, дн. | `triang(7, 10, 18)` | Без изменений |
| | Стоимость `C`, тыс. ₽ | `triang(150, 200, 320)` | Без изменений |

> Для `triang(a, c, b)` указаны минимум `a`, мода `c` и максимум `b`.

## Ожидаемые результаты (Contract v2.1)

Эталонные значения зафиксированы в [`theory_reference.csv`](./theory_reference.csv) и [`metrics_reference.json`](./metrics_reference.json) (`N_SIM = 10 000`, `SEED = 42`):

| Показатель | `BASE` | `ACCEL` | Изменение |
| :--- | :---: | :---: | :---: |
| Теоретическое `E[T_total]`, дн. | 57,83 | 49,50 | −8,33 дн. (−14,4%) |
| Теоретическое `E[C_total]`, тыс. ₽ | 1080,00 | 1190,00 | +110,00 тыс. ₽ (+10,2%) |
| Вероятность срыва срока `P(T_total > 60)` | 35,40% | 1,11% | −34,29 п.п. |
| Вероятность перерасхода `P(C_total > 1200)` | 14,40% | 45,10% | +30,70 п.п. |
| Вероятность успеха `P(T <= 60 и C <= 1200)` | 55,48% | 54,30% | −1,18 п.п. |

Ускорение разработки практически снимает риск нарушения срока, но переносит нагрузку на бюджетный риск. Сценарий `ACCEL` не является безусловно оптимальным без задания приоритета между сроком и бюджетом.

## Запуск и проверка контрактов

### 1. Подготовка окружения

```bash
python -m venv .venv
```

Активация и установка зависимостей из [`requirements.txt`](./requirements.txt):

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

```bash
# Linux / macOS
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Проверка контрактов

Проверка существующих модулей (отсутствующие модули отмечаются как `SKIP`):

```bash
python check_contract.py
```

Финальная строгая проверка (все модули обязательны) и полный расчёт:

```bash
python check_contract.py --strict
python main.py
```

### 3. Порядок работы в Git

Каждый участник работает в отдельной ветке (рекомендуемые имена указаны в [`README_TEAM.md`](./README_TEAM.md), например `islam/generator`) и открывает Pull Request в `main` только после прохождения `python check_contract.py`.

```bash
git checkout -b <имя>/<модуль>
python check_contract.py
```

## Правила работы и ограничения

Полный чек-лист перед сдачей приведён в [§10 `TEAM_TZ_RU.md`](./TEAM_TZ_RU.md#10-чек-лист-перед-сдачей). Основные требования:

1. **Единый источник параметров:** не изменять [`config.py`](./config.py) и не менять порядок вызовов генератора `RNG_ORDER`.
2. **Разграничение ответственности:** редактировать только закреплённые файлы; при необходимости правки контракта согласовывать изменения с лидером.
3. **Строго теория вероятностей:** согласно [`Проект создания РГР.pdf`](./sources/Проект%20создания%20РГР.pdf), в работе не используются методы математической статистики (критерии согласия Пирсона/Колмогорова, доверительные интервалы, оценивание параметров по выборке).
4. **Воспроизводимость чисел:** все итоговые числа в отчёте берутся строго из сгенерированных файлов в [`results/`](./results/), а не переписываются вручную.
5. **Объём отчёта:** итоговый документ (`docx`/`pdf`) должен укладываться в диапазон **8–15 страниц**, включая титульный лист и приложение с кодом.
