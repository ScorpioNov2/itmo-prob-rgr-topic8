## 💡 О чём вообще этот проект? (Объясняем на пальцах за 2 минуты)

Забудьте на пару минут про сложные математические термины и кучу файлов. Вот суть нашей РГР простым человеческим языком:

### 1. Что от нас на самом деле хочет преподаватель?
Представьте, что мы вдевятером — ой, вшестером (плюс лидер = 7 человек) — открыли стартап и решили **сделать новое мобильное приложение с нуля**.
* **Проблема:** Приложение совершенно новое, раньше такое не делали, статистики нет. Мы не знаем точно, сколько дней уйдёт на работу и сколько денег мы потратим.
* **Что у нас есть:** Только примерные оценки по **4 последовательным этапам** (зашиты в [`config.py`](./config.py)):
  1. **Дизайн (`design`):** примерно 5–12 дней, стоит около 80–160 тыс. ₽.
  2. **Разработка (`dev`):** 18–40 дней (но вероятнее всего 25 дней), стоит 400–850 тыс. ₽ (вероятнее всего 550 тыс. ₽).
  3. **Тестирование (`qa`):** 6–14 дней, стоит 100–180 тыс. ₽.
  4. **Маркетинг (`mkt`):** 7–18 дней (вероятнее всего 10 дней), стоит 150–320 тыс. ₽ (вероятнее всего 200 тыс. ₽).
* **Правила игры (цель от заказчика):** Нужно уложиться максимум в **60 дней** (`MAX_DAYS`) и максимум в **1 200 тыс. ₽** (`MAX_BUDGET`).

### 2. Зачем тут Теория вероятностей и Python?
Вместо того чтобы гадать на кофейной гуще *«да ладно, как-нибудь успеем»*, мы заставляем Python **просимулировать разработку этого приложения 10 000 раз** (это и есть метод Монте-Карло):
* Каждый раз компьютер случайно подбрасывает числа дней и денег для 4 этапов и складывает их.
* После 10 000 попыток программа считает, сколько раз мы **не уложились в 60 дней** (сорвали дедлайн) и сколько раз **вышли за 1 200 тыс. ₽** (пробили бюджет).
* **Что получается на базовом плане (`BASE`):** С текущей командой риск сорвать дедлайн составляет аж **35,4%** — это слишком опасно!

### 3. Сценарий «Что, если...» (`ACCEL` — пробуем спасти ситуацию)
Видя такой высокий риск опоздания (35,4%), мы задаём вопрос: **«А что, если нанять ещё одного программиста на этап разработки?»**
* **Плюс:** Код пишется быстрее $\rightarrow$ риск сорвать дедлайн падает с **35,4% до 1,11%** (почти 100% успеваем в срок!).
* **Минус:** Лишний программист просит зарплату $\rightarrow$ риск вылететь за бюджет 1 200 тыс. ₽ подскакивает с **14,4% до 45,1%**.
* **Вывод для защиты:** Идеальной кнопки «сделать хорошо и бесплатно» нет — менеджеру приходится выбирать: *либо просить у инвестора запасной бюджет ради точного релиза, либо экономить деньги и мириться с риском опоздания.*

> **Одним предложением:** мы на Python 10 000 раз «проживаем» создание стартапа, чтобы в цифрах увидеть риск опоздания или перерасхода бюджета и проверить, спасёт ли нас найм дополнительного разработчика.

## 🛠 Как проверить свой код и сдать работу (Git & Проверка)

1. **Установите зависимости** из [`requirements.txt`](./requirements.txt):
   ```bash
   pip install -r requirements.txt
   ```
2. **Работайте только в своей ветке** (не пушьте напрямую в `main` и не меняйте чужие файлы):
   ```bash
   git checkout -b feat/ваш-ник-или-модуль
   ```
3. **Запустите автопроверку контрактов** перед отправкой файла или созданием Pull Request:
   ```bash
   python check_contract.py
   ```
   Если напротив вашего модуля горит **`[OK]`** — можно открывать Pull Request (на этапе финальной интеграции лидер запускает `python check_contract.py --strict`).

## 🚫 5 главных «НЕЛЬЗЯ» (проверьте по [§10. Чек-листу](./TEAM_TZ_RU.md#10-чек-лист-перед-сдачей))

1. **Не менять [`config.py`](./config.py)** и порядок генерации случайных величин (`RNG_ORDER`).
2. **Не править чужие файлы** — каждый отвечает строго за свой список файлов из [`TEAM_TZ_RU.md`](./TEAM_TZ_RU.md).
3. **Не использовать методы математической статистики** (критерии Пирсона/Колмогорова, доверительные интервалы, оценки параметров по выборке) — по [`Проект создания РГР.pdf`](./sources/Проект%20создания%20РГР.pdf) у нас только **Теория вероятностей**.
4. **Не переписывать цифры в Word вручную** — после финальной интеграции все числа в отчёт берутся только из папки [`results/`](./results/).
5. **Не превышать объём отчёта** — итоговый PDF должен быть строго **от 8 до 15 страниц** (включая титульный лист и приложение с кодом).
